# 规格/需求文档审查规则

## 审查维度

### 1. 需求完整性
- 用户故事覆盖所有场景（正常流程、异常流程、边界情况）
- 功能点有明确的验收标准（Given-When-Then 或等价格式）
- 非功能需求已定义：
  - 性能：响应时间（P50/P99）、吞吐量、并发量
  - 安全：认证授权、数据保护级别、合规要求
  - 可用性：SLA（如 99.9%）、容灾等级（RPO/RTO）
  - 可扩展性：未来 6-12 月的增长预估
- 角色与权限矩阵明确（谁可以做什么）
- 外部系统集成接口已列出，协议与数据格式已约定

### 2. 逻辑清晰度
- 需求之间无矛盾，无二义性描述
- 优先级明确（P0/P1/P2，或 MoSCoW Must/Should/Could/Won't）
- 依赖关系清晰（前后端依赖、外部服务依赖、团队间依赖）
- 术语表存在且一致（领域术语有唯一定义）
- 状态机/流程图覆盖关键业务流程

### 3. 可测试性
- 每个需求可独立验证（有明确的测试方法）
- 验收标准可量化（避免"好用""快速""稳定"等主观词）
- 边界条件已显式定义（空值、零值、极大值、超长字符串等）
- 异常场景已遍历（网络超时、服务不可用、数据不一致、并发冲突）
- 测试数据准备方案（含脱敏策略）

### 4. 约束与假设
- 技术约束已显式声明（语言/框架/平台限制）
- 业务假设已记录（如"用户已登录""网络环境正常"）
- 第三方依赖风险已评估（SLA、弃用风险、许可证兼容）
- 需求变更影响范围已预估

## 规格文档检查清单

### 功能完整性
- [ ] 用户故事覆盖所有角色和场景（含异常流程）
- [ ] 每个功能点有可量化的验收标准
- [ ] 错误处理场景已覆盖（网络异常、服务超时、数据异常）
- [ ] 边界条件已定义（空值/零值/极值/超长输入）
- [ ] 并发场景已考虑（竞态、重复提交、幂等性）
- [ ] 角色权限矩阵完整

### 非功能需求
- [ ] 性能要求已明确（RT/QPS/并发数，有具体数值）
- [ ] 安全要求已记录（认证/授权/加密/审计/合规）
- [ ] 可用性 SLA 已定义（含 RPO/RTO 如适用）
- [ ] 可扩展性预估已给出

### 可执行性
- [ ] 需求优先级明确
- [ ] 依赖关系清晰，无循环依赖
- [ ] 术语表存在且一致
- [ ] 外部接口协议与格式已约定
- [ ] 技术与业务假设已记录
- [ ] 第三方依赖风险已评估
