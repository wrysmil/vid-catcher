# 实施计划审查规则

## 审查维度

### 1. 阶段结构
- **第一阶段必须是环境准备**
- 阶段划分清晰，依赖关系明确（标注阶段间的依赖）
- 每个阶段有明确的验证标准（如何判断阶段完成）
- 阶段粒度合理：每个阶段产出可交付、可独立验证
- 有明确的里程碑节点和交付物

### 2. 任务粒度
- 任务可独立执行（2-5 分钟），不依赖人的"判断"或"理解"
- 有明确的输入输出（文件路径、函数签名、数据结构）
- 有验证命令（测试/脚本/手动验证步骤）
- 任务描述包含具体文件路径和代码变更范围
- 避免"实现 XXX 功能"级别的模糊描述

### 3. 环境准备完整性（重点）
- 依赖安装步骤完整（含版本号、安装命令、锁文件）
- 环境变量配置步骤完整（含 .env.example 路径、变量说明）
- 外部服务配置步骤完整（Docker Compose/连接配置/健康检查）
- 环境验证步骤完整（一键验证脚本，验证通过才算环境就绪）
- 平台差异说明（Windows/macOS/Linux 差异处理）

### 4. 测试计划
- 单元测试覆盖核心逻辑（TDD：先写失败测试再实现）
- 集成测试覆盖关键流程（API 端到端、数据库交互）
- 测试数据准备方案（fixture/seed/mock 数据）
- 测试环境与生产环境的差异已标注
- 测试覆盖率目标明确（如 80% 行覆盖、100% 分支覆盖关键路径）

### 5. 风险与回滚
- 高风险任务已标注（数据迁移、架构变更、第三方升级）
- 每个阶段有回滚/撤销方案（数据备份、灰度开关、feature flag）
- 关键任务有备选方案（Plan B）
- 变更影响范围已预估（受影响模块、团队、外部接口）

### 6. 时间与资源
- 任务有预估耗时（不要求精确，但需有量级判断）
- 可并行任务已标注（减少总耗时）
- 阻塞性依赖已高亮（谁等谁、为什么）
- 外部依赖（其他团队/第三方）的交期已确认

## 计划文档检查清单

### 阶段结构
- [ ] Phase 1 是环境准备
- [ ] 每个 Phase 有可验证的完成标准
- [ ] 阶段间依赖关系明确，无隐藏依赖
- [ ] 里程碑节点清晰

### 任务质量
- [ ] 任务有具体文件路径和代码范围
- [ ] 任务有验证命令（不是"手动测试"）
- [ ] 任务粒度控制在 2-5 分钟可执行
- [ ] 产出代码的 Task 以「写失败测试」为 Step 1

### 环境准备
- [ ] 所有依赖有具体版本号
- [ ] .env.example 路径与变量说明完整
- [ ] 外部服务有 Docker Compose 等一键启动方案
- [ ] 环境验证命令可执行（一条命令验证全部）

### 测试
- [ ] 核心逻辑有单元测试计划（TDD 流程）
- [ ] 关键流程有集成测试计划
- [ ] 测试数据准备方案明确
- [ ] 覆盖率目标已设定

### 风险
- [ ] 高风险任务已标注并附带缓解措施
- [ ] 每个阶段有回滚方案
- [ ] 阻塞性依赖已识别
- [ ] 可并行任务已标注

### 可执行性
- [ ] 新成员按计划可独立执行
- [ ] 无"待定"/"后续讨论"的占位任务
- [ ] 无"视情况而定"的模糊分支
- [ ] 外部依赖交期已确认
