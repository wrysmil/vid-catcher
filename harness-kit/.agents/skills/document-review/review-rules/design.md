# 架构/技术设计文档审查规则

## 审查维度

### 1. 整体设计
- 架构图清晰，组件职责明确，分层合理
- 接口定义完整（输入/输出/错误码），契约明确
- 依赖方向正确（上层依赖下层，不反向）
- 模块边界清晰，无循环依赖

### 2. 代码质量与架构（重点）
##### 2.1 高内聚低耦合
- **单一职责**：每个模块/类/函数只做一件事，变更原因唯一
- **接口隔离**：接口精简，不强迫调用方依赖不需要的方法
- **依赖倒置**：高层模块不依赖低层模块，都依赖抽象
- **耦合类型识别**：内容耦合 > 公共耦合 > 控制耦合 > 标记耦合 > 数据耦合，向低耦合方向设计
- **内聚类型识别**：功能内聚 > 顺序内聚 > 通信内聚 > 过程内聚 > 时间内聚 > 逻辑内聚 > 偶然内聚
- 模块间通过接口/消息通信，避免直接访问内部实现
- DI/IoC 容器使用合理，无 Service Locator 反模式

##### 2.2 设计模式
- 识别文档中引用的设计模式，评估是否适用（不滥用、不误用）
- 创建型：工厂方法、抽象工厂、建造者、原型、单例 — 是否真正需要
- 结构型：适配器、桥接、组合、装饰器、外观、享元、代理 — 是否解决实际结构问题
- 行为型：责任链、命令、观察者、策略、模板方法、状态 — 是否简化了复杂交互
- 反模式检查：God Object、Spaghetti Code、Golden Hammer、Premature Optimization、Reinventing Wheel
- 设计模式组合使用是否一致、不冲突

##### 2.3 复杂度控制
- **圈复杂度（Cyclomatic Complexity）**：核心逻辑 ≤ 10，普通方法 ≤ 5
- **认知复杂度（Cognitive Complexity）**：避免深层嵌套（≤ 3 层）、避免多重布尔表达式
- **函数/方法长度**：单函数 ≤ 50 行，参数 ≤ 5 个
- **类/模块行数**：单类 ≤ 500 行，单文件 ≤ 1000 行（含注释）
- **抽象层次一致**：一个函数内不跨越多个抽象级别
- **重复代码（DRY）**：相同的逻辑不在两处以上出现；若出现，是否有合理解释（如独立演进）

##### 2.4 命名与可读性
- 命名遵循项目约定（如 camelCase/PascalCase/snake_case）
- 类名用名词/名词短语，方法名用动词/动词短语
- 避免缩写（除公认缩写外），避免 `data`/`info`/`manager`/`handler` 等模糊词
- 魔法数字已提取为命名常量

### 3. 性能设计（重点）
- **性能目标明确**：QPS/RT/P99 延迟/并发用户数/吞吐量有具体数值
- **瓶颈分析**：识别关键路径，标注可能的性能瓶颈点
- **缓存策略**：
  - 缓存层次（本地缓存/分布式缓存/CDN）及失效策略
  - 缓存预热、穿透、雪崩、击穿的应对方案
- **数据库性能**：
  - 索引设计合理（覆盖查询、避免全表扫描）
  - 慢查询预估，是否有 N+1 风险
  - 连接池配置、读写分离方案
  - 数据量预估（行数/存储量）及分区/分表策略
- **异步与并发**：
  - 合适场景使用异步（消息队列/事件驱动），不阻塞主流程
  - 并发控制策略（乐观锁/悲观锁/分布式锁），避免竞态条件
  - 线程池/协程池大小合理
- **资源管理**：大对象/连接/文件句柄及时释放，避免内存泄漏
- **前端性能**（如适用）：代码分割、懒加载、首屏优化、资源压缩、关键渲染路径

### 4. 环境准备
- **依赖管理**：列出所有第三方依赖及版本、安装命令、锁文件
- **环境变量**：列出所有必需变量、提供 .env.example、说明密钥获取方式
- **外部服务**：列出所有服务依赖、提供 Docker Compose 等本地方案
- **开发环境**：明确运行环境要求、提供环境验证命令
- **测试环境**：测试数据库、Mock 服务、测试数据准备

### 5. 技术细节
- API 设计：RESTful/GraphQL/gRPC 规范一致，请求/响应格式、错误码、版本策略
- 数据库设计：ER 图、表结构、索引、迁移方案、数据一致性保证
- 安全考虑：认证授权（OAuth2/JWT/Session）、数据加密（传输/存储）、输入验证与输出编码、CSRF/XSS/SQL 注入防护、敏感信息脱敏
- 可观测性：日志级别与格式、指标暴露（RED/USE）、链路追踪、告警规则

### 6. 可扩展性与可维护性
- 新增业务场景时的改动范围可控（开闭原则）
- 配置外部化（环境变量/配置中心），不硬编码
- Feature Flag 机制（如需要灰度发布）
- 向后兼容策略（API 版本化、数据迁移兼容）
- 技术债务已标注并有偿还计划

- [ ] 依赖方向正确（依赖抽象而非具体实现）

- [ ] 使用的设计模式已显式命名并说明引入原因

- [ ] 核心方法圈复杂度预估 ≤ 10
- [ ] 最大嵌套层级 ≤ 3
